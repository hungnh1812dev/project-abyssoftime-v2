# Auth Module

`src/modules/auth/**` — clean-architecture module implementing the end-user-facing auth lifecycle: register → OTP-verify → login → refresh/logout, plus forgot/reset-password and a self-lookup `GET /auth/me`. Fully wired: registered in `AppModule`, all routes live. Shares the `User` entity/repository with the `users` module (see [users.md](./users.md)) rather than owning its own user model — this module only adds behavior (hashing, tokens, OTP/reset-token lifecycle) on top of it. Refresh/logout now revoke via the shared `TokenBlacklistService` (see [token-blacklist.md](./token-blacklist.md)) rather than being purely stateless.

## Shared primitives it depends on (`src/common/`)

Deliberately kept outside `auth/` so `users`/`roles`/`permissions` don't have to import the `auth` module directly (preserves "each module independent"):

- `common/token/jwt-token.service.ts` — `JwtTokenService` wraps `@nestjs/jwt`: `signAccessToken`/`signRefreshToken` (15m access; refresh is 7d, or 30d when the payload's `rememberMe` is `true` — separate `JWT_ACCESS_SECRET`/`JWT_REFRESH_SECRET`), `verifyAccessToken`/`verifyRefreshToken`, and `getRefreshTokenMaxAgeMs(rememberMe)` (the 7d/30d value in milliseconds, so callers signing a refresh token and callers setting its cookie's `maxAge` stay in sync from one source instead of duplicating the TTL math). `common/token/token.module.ts` (`TokenModule`) is `@Global()`, so `JwtTokenService` is injectable anywhere without an explicit import.
- `common/guards/jwt-auth.guard.ts` — `JwtAuthGuard` extends `@nestjs/passport`'s `AuthGuard(["jwt", "api-token"])` (backed by `common/strategies/jwt.strategy.ts`'s `JwtStrategy` and `common/strategies/api-token.strategy.ts`'s `ApiTokenStrategy` — either strategy succeeding authenticates the request). Both strategies now read the token from the same `Authorization: Bearer <token>` header (see the `jwt.strategy.ts` entry below), which makes the `["jwt", "api-token"]` order load-bearing: Passport tries `"jwt"` first and falls through to `"api-token"` on a `fail()` (not `error()`) — what `passport-jwt` does on a malformed-JWT decode. API tokens are always `cms_<64-hex>` (from `generateAccessTokenSecret`), never dot-segmented, so they can never parse as a JWT, but that fallthrough depends on both the token shape and the strategy order staying as they are (see the comment on the guard class itself). This file's only repo-owned logic is `handleRequest`, which preserves the original two distinct `401` messages exactly: `"Missing access token"` when neither strategy found a token at all, `"Invalid or expired access token"` for any other failure (bad signature, expired, malformed, or no user).
- `common/strategies/jwt.strategy.ts` — `JwtStrategy` (`passport-jwt`, registered as `"jwt"`) reads the token via `ExtractJwt.fromAuthHeaderAsBearerToken()` (the `Authorization: Bearer <token>` header — no longer the `access_token` cookie; see [Endpoints](#endpoints) for the login/refresh response shape that hands the client this token), verifies it against `JWT_ACCESS_SECRET`, and its `validate(payload)` is a **pure pass-through** returning the already-self-contained `AccessTokenPayload` unchanged — no DB hit.
- `common/strategies/api-token.strategy.ts` — `ApiTokenStrategy` (`passport-http-bearer`, registered as `"api-token"`) hashes the presented bearer token (SHA-256) and looks it up via `IAccessTokenRepository.findByTokenHash`, rejecting on no match or an expired `expiresAt`; `validate()` returns `{ sub: record.updatedBy, permissions: record.permissions }`. Lets the same `JwtAuthGuard` accept either a real user's access token or a scoped API token on one route, both via the same `Authorization: Bearer` header.
- `common/guards/jwt-refresh.guard.ts` / `common/strategies/jwt-refresh.strategy.ts` — `JwtRefreshGuard` extends `AuthGuard(["jwt-refresh"])`, backed by `JwtRefreshStrategy` (`passport-jwt`, registered as `"jwt-refresh"`). Reads the refresh token via its own cookie extractor (`jwtRefreshCookieExtractor`, reading the `refresh_token` cookie exported here as `REFRESH_TOKEN_COOKIE`) — the refresh token is deliberately unchanged by the access-token Bearer-header migration: it's still cookie-only, verified against `JWT_REFRESH_SECRET`. `validate(payload)` now injects `TokenBlacklistService` and, when the decoded payload carries a `jti`, checks whether it's been revoked (by a prior logout or a prior refresh rotation — see [token-blacklist.md](./token-blacklist.md)) before passing the already-self-contained `RefreshTokenPayload` through; a blacklisted jti throws, and a missing jti (a pre-migration token) skips the check entirely. `handleRequest` mirrors `JwtAuthGuard`'s two-message split, worded for a refresh failure: `"Missing refresh token"` / `"Invalid or expired refresh token"` — a revoked token produces the same generic `401` as an invalid one, by design (no wording distinguishes "revoked" from "malformed"). This retires the last hand-rolled auth check in the module — verification for every guarded route (access, refresh, API token) now goes through Passport uniformly.
- `common/strategies/local.strategy.ts` — `LocalStrategy` (`passport-local`, `usernameField: "email"`) absorbs what used to be `LoginService`'s entire credential-checking body — user lookup, the dummy-hash timing mitigation, password compare, `verified`/`roleId` checks, all unchanged — and on success returns `ValidatedLoginUser = { user, role }`, a **route-local** shape used only by the `login` route's `req.user`, deliberately distinct from `AuthenticatedRequest`'s `AccessTokenPayload`. Both strategies are registered via `PassportModule.register({ defaultStrategy: "jwt" })` in `auth.module.ts` (see [Module wiring](#module-wiring)), not the `@Global()` `TokenModule` — see `docs/documents/auth-passport-techstack.md` for the full decision record (why Passport now, the cookie-extractor design, the login-conversion call, and provider-placement rationale). This lays the groundwork for future OAuth strategies (Google/GitHub/...) to register alongside `JwtStrategy`/`LocalStrategy` with no further migration; OAuth itself is not implemented yet. `validate()` opens with a `typeof email/password === "string"` (non-empty) guard throwing `BadRequestException` — a fix from the Phase 4 review: `AuthGuard("local")` runs as a guard, which executes *before* Nest's global `ValidationPipe`, so `LoginDto`'s class-validator decorators never see the login route's body; without this guard, a non-string `password` would reach `bcrypt.compare` unchecked and crash with an unhandled error (500) instead of the old pipe-driven 400.
- `common/guards/permissions.guard.ts` — `PermissionsGuard` reads `@RequirePermissions(...)` metadata and checks it against `req.user.permissions` (read-implies-manager). Used by `roles`/`permissions`/`users`, not by `auth` itself (auth's own routes are either public or only need `JwtAuthGuard`, never `PermissionsGuard`).
- `common/guards/rate-limit.guard.ts` — `RateLimitGuard`, an in-memory per-`(ip, controller class, handler method)` token bucket (`RATE_LIMIT_FPS`/`RATE_LIMIT_BURST` env vars) — see `docs/documents/auth-issues-fix.md` #5 for why the key includes the route, not just the IP. Applied to every auth route that's exposed to unauthenticated callers and could be abused (register/verify-otp/resend-otp/login/forgot-password/reset-password) — not to `refresh`/`logout`/`has-users`.
- `common/types/authenticated-request.ts` / `jwt-payload.ts` — `AuthenticatedRequest = Request & { user: AccessTokenPayload }`, `AccessTokenPayload { sub, roleSlug, level, permissions }`, `RefreshTokenPayload { sub, rememberMe?, jti?, exp? }`. The access token is intentionally self-contained (embeds `roleSlug`/`level`/`permissions` at sign time) so `JwtAuthGuard` never hits the database — a role's permission changes take up to ~15 minutes (the access-token TTL) to apply to an already-logged-in user of that role. `rememberMe` is embedded in the refresh token itself (not tracked server-side) so the 7d-vs-30d choice survives every `/auth/refresh` rotation; a refresh token minted before this field existed won't carry it at runtime even though the type declares it required — `RefreshTokenService` treats a missing value as `false`, not a crash. `jti` (a `randomUUID()` generated inside `JwtTokenService.signRefreshToken`) and `exp` (the standard JWT claim, Unix seconds) are what make a refresh token revocable — both optional for the same reason (`rememberMe`-style pre-migration fallback), consumed by `JwtRefreshStrategy`/`LogoutService`/`RefreshTokenService` — see [token-blacklist.md](./token-blacklist.md).

## Domain port

`domain/ports/email-sender.port.ts` — `IEmailSender { sendOtpEmail({ email, otp }); sendPasswordResetEmail({ email, resetToken }) }`, DI token `EMAIL_SENDER`. Six implementations, selected by the `EMAIL_PROVIDER` env var: `infrastructure/email/console-email.sender.ts` (`ConsoleEmailSender`) just logs both codes via the Nest `Logger` — the zero-config dev/test fallback; `infrastructure/email/smtp-email.sender.ts` (`SmtpEmailSender`) sends real HTML email via the injected `MailerService` (`@nestjs-modules/mailer`, transport configured from `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASSWORD`/`SMTP_SECURE`/`EMAIL_FROM` in `MailerModule.forRootAsync` — see [Module wiring](#module-wiring)); `infrastructure/email/gmail-api-email.sender.ts` (`GmailApiEmailSender`) sends via the raw Gmail API over `fetch` (OAuth2 refresh-token flow, `GMAIL_CLIENT_ID`/`GMAIL_CLIENT_SECRET`/`GMAIL_REFRESH_TOKEN`/`GMAIL_SENDER_EMAIL`) — the one sender not built on an official SDK, a narrow OAuth2-flow exception rather than a repo-wide preference (see `docs/documents/auth-email-providers-techstack.md`); `infrastructure/email/resend-email.sender.ts` (`ResendEmailSender`, `RESEND_API_KEY`), `infrastructure/email/brevo-email.sender.ts` (`BrevoEmailSender`, `BREVO_API_KEY`), and `infrastructure/email/sendgrid-email.sender.ts` (`SendGridEmailSender`, `SENDGRID_API_KEY`) each wrap their vendor's official SDK (`resend`/`@getbrevo/brevo`/`@sendgrid/mail`) — see `docs/documents/auth-email-providers-techstack.md` for the SDK-vs-raw-`fetch` decision and per-provider SDK integration notes (Resend's resolve-not-throw error shape, Brevo's `HttpResponsePromise`, SendGrid's singleton export). The five non-Console senders share one constructor shape: an injected `IEmailTemplateRenderer` for the HTML body, `EMAIL_FROM` read from `ConfigService` for the "from" address, `FRONTEND_URL` read for the reset link. `infrastructure/email/resolve-email-sender.ts` (`resolveEmailSender`) picks the sender implementation at DI-construction time: an explicit `EMAIL_PROVIDER` value (`"gmail" | "smtp" | "resend" | "brevo" | "sendgrid" | "console"`) selects that sender directly; `EMAIL_PROVIDER=auto` (the default) tries each in order — `gmail → smtp → resend → brevo → sendgrid → console` — picking the first whose required env var(s) are set, falling through to `ConsoleEmailSender` if none are. A non-selected sender is never constructed, so an unset API key never breaks a deployment running a different provider.

`infrastructure/email/renderers/email-template-renderer.ts` — `IEmailTemplateRenderer { renderOtpEmail({ otp }); renderPasswordResetEmail({ resetUrl }) }`, DI token `EMAIL_TEMPLATE_RENDERER`, consumed by every sender except `ConsoleEmailSender` (`Smtp`/`Gmail`/`Resend`/`Brevo`/`SendGrid` all render HTML through it). One implementation, bound directly via `{ provide: EMAIL_TEMPLATE_RENDERER, useClass: HandlebarsEmailTemplateRenderer }`: `handlebars-email-template.renderer.ts` (`HandlebarsEmailTemplateRenderer`) compiles the `.hbs` files in `infrastructure/email/templates/handlebars/` (read via `fs.readFileSync` at construction, cached as compiled `Handlebars.compile` functions on the instance, which HTML-escape interpolated values by default) — `nest-cli.json` copies that `.hbs` directory into `dist/src` as a build asset since it isn't a `.ts` file the compiler would otherwise emit.

## DTOs

All in `application/dto/`, all `class-validator`-decorated (the global `ValidationPipe` registered in `src/bootstrap/configure-app.ts` — `{ whitelist: true, transform: true }`, wired up from `src/main.ts` — is what makes these decorators actually enforce anything):

- `register.dto.ts` — `email` (`@IsEmail`), `name` (`@IsString @IsNotEmpty`), `username` (`@Matches(/^[a-zA-Z0-9_.-]{3,32}$/)`), `password` (`@IsString @MinLength(8)`), `accountType` (`@IsBoolean`). No `verified`/`roleId` — those are never client-settable. See `docs/documents/auth-issues-fix.md` #4/#9 for why the password/username rules were added.
- `login.dto.ts` — `email` (`@IsEmail`), `password` (`@IsString @IsNotEmpty`) — no length rule here; this DTO authenticates against an existing hash, it doesn't mint one. `rememberMe` (`@IsOptional @IsBoolean`) — optional, defaults to `false` when omitted; extends the refresh token/cookie from 7 days to 30 days (see [Services & business rules](#services--business-rules)).
- `verify-otp.dto.ts` — `email` (`@IsEmail`), `otp` (`@Matches(/^\d{6}$/)`).
- `resend-otp.dto.ts` — `email` (`@IsEmail`).
- `forgot-password.dto.ts` — `email` (`@IsEmail`).
- `reset-password.dto.ts` — `token` (`@IsString @IsNotEmpty`), `newPassword` (`@IsString @MinLength(8)`).

## Services & business rules

Every service injects `USER_REPOSITORY` (from `users`) and, where noted, `ROLE_REPOSITORY` (from `roles`) or `EMAIL_SENDER`/`JwtTokenService`. All password/OTP hashing uses `bcryptjs` (see [Known gaps](#known-gaps) for why — **not** `Bun.password`, despite this project running on Bun).

- **`RegisterService`** — `409` if `email` or `username` already in use (pre-check). Otherwise: `bcrypt.hash`es the password, generates a 6-digit numeric OTP (`node:crypto`'s `randomInt`), `bcrypt.hash`es the OTP too, creates the user with `roleId: null`, `verified: false`, `otpCodeHash`/`otpExpiresAt` (10-minute TTL), then calls `IEmailSender.sendOtpEmail` with the **plaintext** OTP (the hash is what's persisted). `create()` is wrapped in a try/catch that maps a repository-level `UserAlreadyExistsError` (thrown on a Postgres `P2002`) to the same `409` — a safety net for the rare race where two requests pass the pre-check concurrently; see `docs/documents/auth-issues-fix.md` #2/#3.
- **`VerifyOtpService`** — looks up by email (`404` if not found), `409` if already verified, `400` if there's no pending OTP or it's expired, `400` if the OTP doesn't `bcrypt.compare` match. On success: resolves **both** the `super_admin` and `guest` role documentIds up front, then calls `IUserRepository.completeVerification(documentId, { firstVerifiedRoleId, otherwiseRoleId })`, which atomically (Postgres `Serializable` transaction, retried up to 3× on a `P2034` write conflict) decides whether this is the first user ever to complete verification and assigns the corresponding role, clearing `otpCodeHash`/`otpExpiresAt` (single-use) in the same transaction. "First user" is evaluated at **verification** time, not registration time — whoever *verifies* first gets `super_admin`, not necessarily whoever registered first. The atomicity is what prevents two concurrent verifications from both being granted `super_admin`; see `docs/documents/auth-issues-fix.md` #1.
- **`ResendOtpService`** — `404` if not found, `409` if already verified; otherwise generates and persists a fresh hashed OTP (same 10-minute TTL) and re-emails it.
- **`HasUsersService`** — `(await IUserRepository.count()) > 0`. Backs the public `GET /api/v1/auth/has-users` check (e.g. so a client can show a "set up the first admin account" flow).
- **`LoginService`** — no longer does credential checking; that logic (unchanged: `401` if the email doesn't resolve or the password doesn't `bcrypt.compare`, same generic message either way; the not-found path still runs a `bcrypt.compare` against a precomputed dummy hash for timing parity; `403` if `!user.verified`, checked *after* credentials so an unverified user still gets routed to "verify your email" instead of a generic auth failure) now lives in `common/strategies/local.strategy.ts`'s `LocalStrategy.validate()`, invoked via `AuthGuard("local")` on the `login` route — see [Shared primitives](#shared-primitives-it-depends-on-srccommon) above. `LoginService.execute({ user, role }: ValidatedLoginUser, rememberMe: boolean): LoginResult` is now a **synchronous**, token-signing-only method: given the already-validated `user`/`role` Passport handed it and the `rememberMe` flag read off the request body by the controller, signs an access token (embedding `roleSlug`/`level`/`permissions`) + refresh token (`{ sub: documentId, rememberMe }`) via `JwtTokenService`, and returns `refreshTokenMaxAgeMs` (7d/30d, from `JwtTokenService.getRefreshTokenMaxAgeMs`) alongside both tokens so the controller never re-derives the TTL itself.
- **`RefreshTokenService`** — no longer verifies the refresh JWT itself; `JwtRefreshGuard`/`JwtRefreshStrategy` (see [Shared primitives](#shared-primitives-it-depends-on-srccommon)) does that ahead of the controller, so `execute(sub, rememberMe, jti?, exp?)` takes an already-verified subject/flag/jti/exp straight from `req.user`. Re-fetches the user **and role fresh from the database** (not from stale token claims — this is what makes a role/permission change take effect on refresh instead of waiting out the full access-token TTL). Right after that, and only when the old token carried both `jti`/`exp`, it **atomically claims** the just-consumed jti (`reason: "rotation"`) via `TokenBlacklistService.tryClaim` — a Postgres unique-constraint `INSERT`, not a plain check-then-write — **before** signing the new pair; losing the claim (a concurrently-racing refresh of the same cookie got there first) rejects immediately with no tokens minted. Only after a won (or skipped, for pre-migration tokens) claim does it issue a new access token and **rotate** the refresh token — re-signing it with the same `rememberMe` the verified token carried. The controller falls back to `false` if `req.user.rememberMe` is absent (for tokens minted before this feature shipped), so a "remembered" session stays 30d-lived across every subsequent refresh rather than reverting to 7d after the first rotation. This atomic-claim-before-signing ordering is what makes refresh tokens genuinely single-use, including under concurrent replay — see [token-blacklist.md](./token-blacklist.md#concurrency-atomic-claim-vs-check-then-write) for the race this closes and how it was found (a five-axis review, not the original plan).
- **`LogoutService`** (`application/services/logout.service.ts`) — the one route that used to have no service at all. Takes the raw `refresh_token` cookie value (`string | undefined`); any verification failure (missing, garbage, expired) is swallowed so logout stays a public, always-`200`, idempotent route. On a successful verify, and only when the decoded payload carries both `jti`/`exp`, blacklists it (`reason: "logout"`) via `TokenBlacklistService.blacklist` — wrapped in its own try/catch so a transient DB error on the write can't turn this always-`200` route into a `500`. The controller still clears the `refresh_token` cookie unconditionally afterward, byte-identical to before this feature. See [token-blacklist.md](./token-blacklist.md).
- **`ForgotPasswordService`** — looks up by email; generates the random 32-byte token (`node:crypto`'s `randomBytes(32).toString("hex")`) and its **SHA-256** hash unconditionally, on both branches, before checking whether a user was found — if not found, **resolves successfully anyway** (no DB write, no email sent) to avoid leaking which emails are registered via the response; doing the same crypto work on both paths also avoids leaking it via response timing (partial mitigation only — the known-email branch still does an extra DB write + email dispatch the unknown-email branch doesn't). If found: stores the hash (not bcrypt — it's already a high-entropy random token, not a low-entropy secret that needs slow hashing) with a 1-hour expiry, and emails the **plaintext** token via `IEmailSender.sendPasswordResetEmail`.
- **`ResetPasswordService`** — SHA-256-hashes the incoming `token` and looks up by `IUserRepository.findByResetTokenHash`; `400` ("Invalid or expired reset token") if not found or if `resetTokenExpiresAt` is missing/past. Otherwise `bcrypt.hash`es `newPassword` and clears `resetTokenHash`/`resetTokenExpiresAt` (single-use).
- **`GetMeService`** — backs `GET /api/v1/auth/me`. `IUserRepository.findById(req.user.sub)` → `401 UnauthorizedException` ("Invalid session") if the account was deleted after the access token was issued (the first route to re-check this). If `user.roleId === null`, returns `role: null` with no role lookup. Otherwise `IRoleRepository.findById(user.roleId)` → `404 NotFoundException` if it doesn't resolve (matches `UpdateUserRoleService`'s existing handling of the same nullable `findById` contract, see [users.md](./users.md)). Role/permissions are read **fresh from the DB** on every call, not from the access token's embedded claims — the token can't carry `role.documentId`/`role.name` anyway, so a DB lookup is mandatory regardless; the accepted tradeoff is that a role edit can take up to the access token's ~15-minute TTL to be reflected here, same as `PermissionsGuard`'s enforcement.

## Endpoints

`presentation/auth.controller.ts`, `@Controller("/api/v1/auth")`. `login`/`refresh` return `accessToken` in the JSON response body and set `refresh_token` as an httpOnly cookie (`secure`/`sameSite` from `COOKIE_SECURE`/`COOKIE_SAMESITE` env vars; `maxAge` ~7d by default or ~30d when the request body's `rememberMe` was `true`) — the access token is never set as a cookie; the client holds it in memory and sends it back as `Authorization: Bearer <token>` on every subsequent request. `logout` clears the `refresh_token` cookie only (there's no access-token cookie to clear). No route ever returns a password hash, OTP hash, or reset-token hash in its response body — every response is `{ message }` (`{ message, accessToken }` for login/refresh, or `{ hasUsers }`).

| Method | Path                        | Service                | Guard                          | Notes |
| ------ | --------------------------- | ----------------------- | ------------------------------- | ----- |
| `POST` | `/api/v1/auth/register`        | `RegisterService`       | `RateLimitGuard`                 | Public |
| `POST` | `/api/v1/auth/verify-otp`      | `VerifyOtpService`       | `RateLimitGuard`                 | Public |
| `POST` | `/api/v1/auth/resend-otp`      | `ResendOtpService`       | `RateLimitGuard`                 | Public |
| `GET`  | `/api/v1/auth/has-users`       | `HasUsersService`        | none                              | Public |
| `POST` | `/api/v1/auth/login`           | `LoginService`           | `RateLimitGuard`, `AuthGuard("local")` | Public; returns `accessToken` in the body, sets the `refresh_token` cookie |
| `POST` | `/api/v1/auth/refresh`         | `RefreshTokenService`    | `JwtRefreshGuard`                | Public; returns a rotated `accessToken` in the body, rotates the `refresh_token` cookie, and blacklists the just-consumed refresh token's `jti` (single-use rotation — see [token-blacklist.md](./token-blacklist.md)) |
| `POST` | `/api/v1/auth/logout`          | `LogoutService`          | none                              | Public, always `200`, idempotent; clears the `refresh_token` cookie and blacklists its `jti` (see [token-blacklist.md](./token-blacklist.md)) |
| `POST` | `/api/v1/auth/forgot-password` | `ForgotPasswordService`  | `RateLimitGuard`                 | Public |
| `POST` | `/api/v1/auth/reset-password`  | `ResetPasswordService`   | `RateLimitGuard`                 | Public |
| `GET`  | `/api/v1/auth/me`              | `GetMeService`           | `JwtAuthGuard`                    | Requires `Authorization: Bearer <accessToken>`; no `PermissionsGuard` — see below |

Every route here is public (unauthenticated) by design, **except `GET /auth/me`** — this is the module whose job is to *establish* identity, and `/me` is the one route that reads an already-established session back. `/me` uses `JwtAuthGuard` only, never `PermissionsGuard` (matching the existing no-permission-required precedent at `UserController.update`, `PUT /users/:id`) — permission-gating a "what am I allowed to do" endpoint would be circular. Everything under `/api/v1/users`, `/api/v1/roles`, `/api/v1/permissions` is what actually requires `JwtAuthGuard` + `PermissionsGuard` (see [users.md](./users.md), [roles.md](./roles.md), [permissions.md](./permissions.md)).

## Module wiring

`auth.module.ts` imports `UserModule` + `RoleModule` + `MailerModule.forRootAsync({ inject: [ConfigService], useFactory: ... })` (the SMTP transport config, moved here from `SmtpEmailSender`'s constructor so the transport is built once at module-init time rather than per-instance) + `PassportModule.register({ defaultStrategy: "jwt" })`, registers the controller, all eight services (including `GetMeService`), `JwtStrategy`, and `LocalStrategy`, and binds two providers: `EMAIL_TEMPLATE_RENDERER` via `{ useClass: HandlebarsEmailTemplateRenderer }`, then `EMAIL_SENDER` via `{ useFactory: resolveEmailSender, inject: [ConfigService, MailerService, EMAIL_TEMPLATE_RENDERER] }` (env-driven 6-way provider selection — `gmail`/`smtp`/`resend`/`brevo`/`sendgrid`/`console` — see [Domain port](#domain-port)). Both strategies are registered here rather than the `@Global()` `TokenModule` since `LocalStrategy` needs `USER_REPOSITORY`/`ROLE_REPOSITORY` — already reachable via the `UserModule`/`RoleModule` imports — and `TokenModule` stays untouched, still used by `RefreshTokenService` and `LoginService`'s signing tail; Passport's underlying registry is process-wide, so `AuthGuard("jwt")` guards in *other* modules (users/roles/permissions/media/document/content-type) still resolve `JwtStrategy` correctly without those modules importing `AuthModule` themselves. Imported into `src/app.module.ts` alongside the other feature modules and `SeedModule` (the boot-time seeder that inserts the 6 default permissions + 4 default roles — `super_admin`/`admin`/`editor`/`guest` at levels 100/50/0/0 respectively — that `VerifyOtpService`/`LoginService` resolve against; see `src/bootstrap/seed-default-data.service.ts`).

## Known gaps / deliberate scope decisions

- **`bcryptjs`, not `Bun.password`, despite this project running on Bun.** The original plan used `Bun.password.hash`/`.verify` (Bun's built-in hashing API, no new dependency). That broke immediately: this project's test suite runs via `bun run test` → Jest, and Jest's `testEnvironment: "node"` executes every test file under a real Node.js process regardless of which binary launched the Jest CLI — `Bun` is `undefined` inside test files. Switched to `bcryptjs` (pure-JS, portable across both runtimes) for all password/OTP hashing; see `tasks/plan.md` finding 3 for the full account.
- **Resolved: refresh tokens now have server-side revocation.** Logout and rotation both blacklist the consumed refresh token's `jti` via the shared `TokenBlacklistService` (Postgres-backed, optional Redis cache) — a logged-out or already-rotated refresh token is rejected by `JwtRefreshStrategy` with the same generic `401` as an invalid one. See [token-blacklist.md](./token-blacklist.md) for the full design, and its own known gaps: refresh tokens minted before this shipped carry no `jti` and remain unrevokable for the rest of their original TTL; a leaked **access** token is still exploitable for up to its 15-minute natural expiry regardless of logout/rotation (unchanged — access tokens are deliberately never persisted, see `JwtAuthGuard`/`AccessTokenPayload` above); there's no scheduled sweep of expired blacklist rows.
- **No e2e tests** for the full register→verify→login→refresh round trip (consistent with how `users`/`roles`/`permissions` were scoped — pure unit tests with mocked repositories/ports only). `src/bootstrap/configure-app.spec.ts` does exercise one real HTTP round trip (against `/api/v1/permissions`, with the auth guards overridden), but only to prove the global `ValidationPipe`/`cookie-parser` wiring, not this module's own routes.
- **Manual end-to-end verification is still outstanding** as of this writing — every unit-testable piece is covered (`bun run test:cov`/`build`/`lint` all clean), but nobody has yet run `bun run start:dev` against a real database and walked through register → verify → login → refresh → logout, or the two-user `super_admin`-then-`guest` role-assignment scenario, by hand.
- **Resolved:** `ConsoleEmailSender` was the only `IEmailSender` (flagged in `docs/documents/auth-issues-fix.md` #10 as a deliberate, deferred provider decision). Five real senders now exist alongside it — `SmtpEmailSender`, `GmailApiEmailSender`, `ResendEmailSender`, `BrevoEmailSender`, `SendGridEmailSender` — selected env-driven via `resolveEmailSender` (`EMAIL_PROVIDER`, `"auto"` order `gmail → smtp → resend → brevo → sendgrid → console`) — see [Domain port](#domain-port) and `docs/documents/auth-email-providers-techstack.md`/`docs/documents/auth-email-techstack.md` for the provider decision rationale. Real credentials for each provider (`SMTP_*`/`GMAIL_*`/`RESEND_API_KEY`/`BREVO_API_KEY`/`SENDGRID_API_KEY`) plus `EMAIL_FROM`/`FRONTEND_URL` still need to be filled in by the user in their own `.env`, and a real send confirmed for each — none of the six providers has had a manual send verified against a real inbox as of this writing (tracked in `tasks/todo.md`).
- **Email HTML rendering moved to Handlebars `.hbs` files, not TS template functions.** `SmtpEmailSender` originally built a `nodemailer` transport directly and called `buildOtpEmailHtml`/`buildResetPasswordEmailHtml` inline; it now depends on `MailerService` (`@nestjs-modules/mailer`) for transport/sending and an injected `IEmailTemplateRenderer` (`HandlebarsEmailTemplateRenderer`, the sole implementation) for HTML — see [Domain port](#domain-port). `.hbs` files let non-TS-comfortable contributors (or a future CMS-driven template editor) edit email markup without touching `.ts` template functions, and `{{value}}` HTML-escapes by default. A parallel TS-template-literal renderer and an `EMAIL_TEMPLATE_ENGINE` toggle existed briefly during evaluation; both were removed since maintaining two copies of the same two templates had no upside once Handlebars was settled on — see `docs/documents/auth-techstack.md`'s "Email template rendering" table.
- **`TRUST_PROXY` defaults to `"1"`** (`src/config/env.validation.ts`), assuming exactly one reverse-proxy hop in front of this app (this project is deployed on Render, which fronts every service with a single edge proxy). If the deployment topology changes (e.g. an additional CDN/LB hop, or direct exposure with no proxy at all), this env var must be updated accordingly — see `docs/documents/auth-issues-fix.md` #6.
